# QA Audit — 2026-08-31

First-pass diagnostic audit (UX/a11y, frontend performance, backend
reliability/data/security, structural). Catalog only when written — see
"Status" column as items get resolved. Full narrative for each finding
lives below the priority table; don't re-derive it, this *is* the record.

Session context for whoever picks this up: this is a personal exercise
knowledge base and workout platform (see root `CLAUDE.md` and
`PROJECT_PLAN.docx` in the Drive folder for full project context), for a
small trusted group behind one shared site password. This audit followed
a session that also fixed a month-long total login outage, an N+1 query,
a Windows path-separator lint bug, redundant "Workout" suffixes in
scraped day names, dates rendering in UTC instead of viewer-local time,
an inconsistent muscle-diagram component between two screens, and the
workout generator's Goal/Experience wizard steps ignoring the active
profile. All of those are already fixed, committed, and deployed — see
`CHANGELOG.md` and `docs/technical/lessons-learned.md` for the full
story on each, including two lessons-learned entries specifically about
this session's own QA methodology mistakes (treating "there's a comment
explaining this" as equivalent to "this is still correct").

## Full findings, by audit category

### 1. UX, Layout & Accessibility
- No brute-force lockout on site password / admin login, unlike the PIN
  system (`src/lib/pin.ts` has real 5-attempt/15-min lockout;
  `src/app/login/actions.ts` and `src/app/admin/login/actions.ts` do a
  plain constant-time compare with no attempt tracking at all).
- `exercise-item-guidance.tsx`'s guidance panel is a native `<details>` —
  functionally fine, minimal but adequate a11y.
- Generator's "no exercises matched" error doesn't connect the failure
  back to "you didn't pick any equipment" for a first-time user.
- **Checked and solid, not a gap**: icon-only buttons consistently carry
  `aria-label` (sampled 5/5 correct); status is never color-only
  (`SessionStatusBadge` pairs icon + text); drag-and-drop block
  reordering has a working keyboard fallback (`dnd-kit` `KeyboardSensor`
  + `sortableKeyboardCoordinates`); touch targets are lint-enforced
  (44px/56px), not ad hoc.

### 2. Frontend Performance & Logic Bloat
- `exercise-performance-detail.tsx`, `exercise-trend-chart.tsx`,
  `personal-records-panel.tsx`, `volume-chart.tsx` are all `"use client"`
  for an undocumented reason: they call `.toLocaleDateString()` directly
  and need browser-local timezone (same bug class fixed elsewhere this
  session in Server Component call sites via the new `FormattedDate`
  component). No comment marks this, so a future "simplification" back
  to Server Components would silently reintroduce the UTC-date bug.
- `exercise-item-guidance.tsx` is `"use client"` with no hooks/handlers —
  the native `<details>` element does all the interactivity; could be a
  Server Component.
- Exercise library grid (1,271 exercises, server-paginated — bounded, so
  lower severity) has no memoization/virtualization. Not measured — a
  hypothesis to profile, not a confirmed bottleneck.
- Two largest files: `dropdown-menu.tsx` (268 lines, expected size for a
  shadcn/Radix wrapper, not bloat) and `profile/actions.ts` (347 lines,
  bundles create/update/delete/onboarding/PIN + admin-initiated deletion
  in one file — a structural note, not a perf issue on its own).
- **Checked and solid**: no raw-string SQL interpolation anywhere (the
  one `sql\`\`` usage interpolates a Drizzle column reference, the safe
  pattern); pagination is server-enforced via a fixed `PAGE_SIZE`, not
  client-suppliable.

### 3. Backend Reliability, Data & Security
- **Highest severity**: `logSet()` in `src/app/session/actions.ts` — the
  function that writes real, immutable performance history — has zero
  input validation. No Zod, unlike `updateItemPrescription`/
  `updateBlockRest` in `workouts/[id]/edit/actions.ts:146-149`, which
  properly bound sets/reps/rest. `weight`/`reps` accept anything
  (negative, `NaN` — Postgres `numeric` accepts the literal `NaN` and
  stores it, doesn't reject it — or absurd magnitudes); `notes` has no
  length cap. Directly threatens the app's own "history is never
  silently wrong" promise.
- No top-level `error.tsx`/`global-error.tsx` — only two route-specific
  `not-found.tsx` files exist. An uncaught exception (e.g.
  `requireOwnedSession` throwing `"Session not found"` for a stale ID)
  falls through to Next's default unstyled error page, bypassing the
  app's own `ErrorState` component built for exactly this.
- 6 of 9 Server Action files skip Zod: `build/actions.ts`,
  `build/library/[id]/actions.ts`, `workouts/actions.ts`,
  `admin/login/actions.ts`, `login/actions.ts`, `session/actions.ts`.
  The login ones are low-risk (credential compare, not structured data);
  `workouts/actions.ts` and the `build/` ones warrant the same check
  `edit/actions.ts` already has.
- `proxy.ts`'s general site-session check runs before the
  `/admin`-specific branch, for any path — currently harmless only
  because every existing `/admin/*` page independently re-checks
  `getAdminSessionStatus()`. A future admin page that forgets that check
  would be silently reachable by any site-password holder. Already
  surfaced once this session; you chose not to fix it then.
- `getProfileDetail()` in `db/queries/admin.ts`: `completedSessionCount`
  computed via `.filter((s) => s.id)`, a no-op (`id` always truthy) — a
  duplicate of `sessionCount`, not what it claims to be.
  `totalVolume` is hardcoded to `0`.
- **Checked and solid**: FK constraints are real and enforced (cascade
  deletes verified correct earlier this session); every Server Action
  mutating session data checks `profileId` ownership first — no IDOR
  found; auth uses constant-time comparison and HMAC-signed sessions
  throughout, not naive `===`.

### 4. Decision & Structural Critique
- Generator's exercise selection uses the wizard's submitted
  `experienceLevel`; each exercise's guidance panel uses
  `profile.experienceLevel` directly (`generate/actions.ts:94`,
  `userLevel`). Even with matching *defaults* now (fixed this session),
  a user who deliberately generates a harder one-off workout than their
  profile default will see a workout whose selected exercises match one
  difficulty and whose coaching cues match another, on the same screen.
  Needs a decision: should a per-generation override also override
  guidance, or is the split intentional?
- Six credential/session concepts for a "small trusted group, one shared
  password" app: `SITE_PASSWORD`+`site_session`, `ADMIN_TOKEN`+
  `admin_session`, per-profile PIN+`activeProfileId`. Already logged as
  PROJECT_PLAN section 4 item 55 after the login-outage postmortem.
- `/profile` vs `/my-profile` mid-migration (Epic P not started — item
  51): two routes for overlapping purposes, gated by an "admin at the
  profile level" concept the data model doesn't have yet.
- `PROJECT_PLAN.docx` (generated from `scripts/docs/project-plan.ts`)
  lags at least two shipped epics (P, Q) and the exercise count (1,271
  live vs. 1,218 documented) — same root cause as the doc-staleness
  already noted in item 55's own writeup.
- `ENHANCEMENTS.docx` (canonical per `CLAUDE.md`) and
  `public/enhancements.json` (a lighter admin-dashboard view, added the
  same commit that broke login) are two unsynced backlogs. Neither
  references the other.
